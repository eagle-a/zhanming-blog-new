# 周汇报投稿规范

本规范根据以下三次实际投稿整理：

- 2026-09-09：传输线、ADC/DAC 与模拟电路学习；
- 2026-09-13：模拟电路阅读、焊接排故与 LM2596 PCB 设计；
- 2026-09-18：ROGlite 首板焊接、ADC/DAC 调试与性能测试。

这是内容、结构和排版规范。一次性投稿码、审批权限和投稿命令仍以 [`AI_SUBMISSION_GUIDE.md`](AI_SUBMISSION_GUIDE.md) 为准。

## 一、文章定位

周汇报是写给老师看的工作记录，不是论文、实验室日志或营销文案。文章需要回答四个问题：

1. 这几天具体做了什么；
2. 得到了什么结果；
3. 哪些结论已经被证据支持；
4. 哪些问题还没有解决。

写作重点是过程、证据和判断，不是堆砌术语。没有完成的测试必须明确写“未完成”“未验证”或“只能说明……”，不能用推测替代结果。

## 二、文件格式

每篇周汇报必须使用 Markdown，并包含完整 frontmatter：

```markdown
---
title: '研一上，第3周：本周主题'
slug: weekly-report-2026-09-18
summary: '一句话说明本周完成的工作和主要结果。'
tags: ['学习汇报', '项目名', '主题']
category: 工作记录
date: 2026-09-18
---

# 研一上，第3周：本周主题

**日期：**2026 年 9 月 18 日（学习周期：9 月 14 日—9 月 18 日）

老师好，现汇报本周的学习和工作情况。
```

字段要求：

| 字段       | 要求                                                                |
| ---------- | ------------------------------------------------------------------- |
| `title`    | 使用“研一上，第 N 周：主题”格式；主题具体，不写“本周总结”这类空标题 |
| `slug`     | 只用小写英文、数字、短横线或下划线；推荐 `weekly-report-YYYY-MM-DD` |
| `summary`  | 一句话，说明工作范围和主要结果；不要写未经验证的性能承诺            |
| `tags`     | 3—6 个，使用项目、器件、方法和文章类型等关键词                      |
| `category` | 周汇报统一使用 `工作记录`                                           |
| `date`     | 使用 `YYYY-MM-DD`；需要明确时区或时间再使用完整 ISO 时间            |

正文第一个 H1 应与 `title` 一致。投稿工具会去除重复 H1，但源文件仍应保持一致，便于本地预览和归档。

## 三、推荐结构

根据工作类型选择下面结构，不要求每篇都机械套用全部章节。

```markdown
## 一、主要学习内容

### 1. 资料阅读或理论分析

### 2. 硬件、软件或仿真工作

### 3. 测试与排故

## 二、阶段性认识

## 三、下一步计划
```

硬件调试周报可以改成：

```markdown
## 一、硬件调试

## 二、ADC 测试

## 三、DAC 测试

## 四、目前的问题

## 五、下一步计划
```

### 1. 开头

开头用一段话交代本周范围和当前状态。应直接说明完成了哪些链路，不要从抽象感想开始。

推荐写法：

> 本周完成了 FPGA 下载、UART 上传和 ADC 采集链路调试，RF2 已在当前固件和测试条件下完成稳定性测试；RF1 和全速采集仍未验收。

### 2. 学习或设计内容

说明阅读、仿真、原理图、PCB 或代码工作，并写出具体收获。理论内容必须和项目联系起来，例如端接、噪声、时钟、反馈补偿、差分输入或回流路径。

不要只写“学习了某某知识”。应写清楚它如何影响器件选择、参数设置或测试方案。

### 3. 硬件调试

按“现象 → 排查方法 → 证据 → 当前状态”描述问题：

```text
现象：某数据位固定为 0 或 1。
排查：使用测试码、上下拉和示波器逐段检查。
证据：FPGA 侧有波形，排阻另一侧没有对应波形。
状态：返修后功能恢复，但仍需长时间验证。
```

不要把“怀疑原因”写成“已经确认的根因”。例如 FPGA 同时开关噪声、电源回流和焊点问题可以列为待定位因素，除非已有隔离测试证明其中一个是唯一原因。

### 4. 性能测试

所有数值必须同时写测试条件：输入频率、输入幅度、采样率、有效保存率、负载、仪器或算法口径，以及样本数量。

应区分以下三类结果：

- 芯片或器件指标：只有在测试条件和测量链满足数据手册要求时才能这样写；
- 整板或整链结果：例如“信号源 + 前端 + ADC 的 SNR”；
- 设计或模型结果：例如原理图仿真、零阶保持理论衰减、满量程外推值。

推荐写法：

> 在约 -5.8 dBFS 输入、16.667 MSPS ADC 时钟和 8.333 MSPS 有效保存率下，RF2 整条采集链的 SNR 中位数为 58.19 dB。

不推荐写法：

> AD9251 的 SNR 是 58.19 dB。

如果仪器导出只有 8 bit、三帧实际是同一缓存、原始 CSV 已删除或测试条件不一致，必须在正文中说明限制，不能把结果写成高精度重复性或器件极限指标。

### 5. 阶段性认识

本节只保留 1—3 条真正改变判断的认识。例如：

- 名义位数不等于系统有效精度；
- 降低写入活动可以规避跳码，但不等于物理根因已修复；
- DRC/ERC 通过不等于实物已经满足负载、纹波和温升指标。

不要重复前文数据，也不要写泛泛的励志总结。

### 6. 问题和下一步

问题清单要写可执行、可验证的事项，例如“返修 ADB6 后做 100 帧长测”“在 ADC 去耦电容处测纹波”“核对采购订单和来料标签”。

下一步计划按优先级列 3—5 项，避免写“继续优化”“继续学习”这类无法验收的句子。

## 四、图片规范

图片不是装饰，必须服务于一个明确结论。三次投稿形成的统一规则如下：

1. 图片紧跟在对应段落后面，不把所有图片堆到文章末尾；
2. 图片路径使用线上绝对路径，例如 `/api/media/blog/weekly-report-2026-09-18/cf496319720762f3e4f7917ab42f946efdea90548f3c4f0bf980557f317966c9.png`；
3. 每张图片必须有图注，格式统一为：`图 N：说明画面内容、测试条件或能支持的结论。`；
4. 图注同时说明证据边界，例如“设计渲染，不代表实板焊接质量”“仿真结果，不能替代实测”“整条测量链结果，不是单机指标”；
5. 图号从 1 开始连续，不能重复、跳号或引用不存在的文件；
6. 原理图、PCB 渲染、示波器截图、实物照片和数据分析图要在图注中明确区分；
7. 已删除的图片不要在文章或投稿资源中恢复；
8. 图片上传到 Blob 后统一用 `/api/media/blog/<slug>/<sha256>.<ext>` 引用，仓库里不再保留副本；原图留在研究资料目录；
9. 图片文件名使用 ASCII、小写和短横线或下划线，避免空格、中文和括号；
10. 图片必须实际存在，投稿前逐一检查 Markdown 路径和线上资源路径。

## 五、语言要求

### 应该使用

- “已完成”“观察到”“测试显示”“在当前条件下”“尚未验证”；
- “约”“量级”“条件通过”“可用于联调”；
- 先写事实，再写判断，最后写限制。

### 不要使用

- “完全成功”“达到芯片极限”“性能优异”等无证据评价；
- “应该是”“大概是”但不说明验证计划；
- 把仿真、设计目标、外推值和实测值混写；
- 把供应商责任、芯片真伪或单一器件根因写成已证实结论，除非有订单、来料或隔离证据；
- 大段复述工程审计、文件哈希、工具过程或 AI 对话记录。
